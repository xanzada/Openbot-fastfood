# Что нужно доработать на стороне hub.alemi.kz

Документ для разработчика hub.alemi.kz. Проверено на живом стенде **12.08.2026**,
ресторан `prestige` (Crazy Суши), `catalog.context.get` версия каталога `1453`.

Со стороны бота (WhatsApp-ассистент) всё описанное ниже уже поддержано — ждём
только данных. Ничего в hub.alemi.kz мы не меняем и не имеем доступа на запись.

---

## Как бот обращается к хабу (контекст, ничего менять не надо)

```
POST https://hub.alemi.kz/v1/integrations/bot/commands
Content-Type: application/json

X-Platform-Instance:   prestige
X-Command-Id:          <uuid, идемпотентность>
X-Command-Timestamp:   <unix seconds, окно 5 минут>
X-Command-Signature:   HMAC-SHA256(secret, timestamp + "." + rawBody)

{ "command": "<имя>", "command_id": "...", "data": { ... },
  "instance": "prestige", "schema_version": 1 }
```

Работающие команды: `runtime.status.get`, `order.context.get`, `order.status.get`,
`catalog.context.get`, `crm.lead.upsert`, `crm.today.get`,
`analytics.daily.upsert`, `customer.access_link.issue`.

## 1. Нет команды для чтения заметок смены — приоритет высокий

**Что происходит сейчас.** Оператор может создать заметку смены («сегодня нет
лосося», «кухня загружена, +20 минут», «промо на донер до 18:00»). Бот такие
заметки читает и учитывает в ответах гостю. Но записать заметку может **только**
сам бот, в свою память (Redis). Команды, которая бы вернула заметки *из хаба*, не
существует: мы перебрали 11 вероятных имён (`shift_note.list`,
`shift_notes.get`, `runtime.shift_notes.get` и другие) — все отвечают **400**.

**Почему это важно.** Если бот в момент создания заметки был недоступен
(перезапуск, деплой, обрыв связи), заметка остаётся видна только в панели хаба и
до гостя не доходит. Бот про неё никогда не узнает, потому что спросить не у
кого. То же самое, если оператор в принципе привык работать в панели хаба, а не
через бота: тогда его заметки не влияют на ответы вообще.

**Что нужно сделать.** Одно из двух — что удобнее.

Вариант A, отдельная команда `shift_note.list`:

```json
// запрос
{ "command": "shift_note.list", "data": { "active_only": true } }

// ответ
{
  "notes": [
    { "id": "019fd1...", "text": "Лосося нет до вечера",
      "expires_at": "2026-08-12T18:00:00Z" }
  ]
}
```

Вариант B, массив внутри уже существующего `runtime.status.get`:

```json
{ "shift_notes": [
    { "id": "019fd1...", "text": "Лосося нет до вечера",
      "expires_at": "2026-08-12T18:00:00Z" } ] }
```

Требования к полям:

- `id` — строка, стабильная (нужна, чтобы одну и ту же заметку не применять дважды);
- `text` — строка, обычный человеческий текст, до ~300 символов;
- `expires_at` — ISO-8601 в UTC. Если заметка бессрочная — `null`. Просроченные
  заметки бот сам отбросит, но лучше их вообще не присылать при `active_only: true`;
- пустой список — это `{"notes": []}`, а не `404` и не ошибка.

Вариант B немного лучше: заметки поедут вместе со статусом, лишнего запроса на
каждый диалог не будет.

## 2. Контент меню — 4 конкретные ошибки

Это не про код, это про данные в каталоге. Бот отдаёт гостю **ровно то, что
пришло из хаба**, поэтому каждая ошибка ниже видна гостю в WhatsApp дословно.

### 2.1 Дубль в названии

Позиция называется **«Римская пицца Римская пицца»**. Гостю так и приходит.
Должно быть «Римская пицца».

### 2.2 Два блюда в неверных категориях

Сейчас в каталоге всего 4 категории: `Суши`, `Донер`, `Пиццы`, `Роллы`. И в них:

| Позиция | Категория сейчас | Должна быть |
|---|---|---|
| **Цезарь** (3000 ₸) | `Суши` | `Салаты` — категории пока нет, надо создать |
| **4 сезона** (2500 ₸) | `Суши` | `Пиццы` |

Почему это важнее, чем выглядит: когда гость просит «покажи пиццы», бот
фильтрует по категории. «4 сезона» в такой выдаче не появится, хотя она есть в
меню, — то есть гость просто не увидит блюдо, которое хотел заказать. И
наоборот: на «что есть из суши» бот предложит салат Цезарь.

### 2.3 Описания забиты текстом для сайта

У **6 из 12** позиций поле `description` длиннее 200 символов — это абзацы
статейного текста («история блюда», «в Италии традиционно…»). Самое длинное —
320 символов у «Гункан-маки», 281 у «Цезаря».

Для сайта это нормально, для WhatsApp — нет: сообщение становится стеной текста,
и гость перестаёт читать. Просьба одно из двух:

- либо сократить `description` до 1–2 фраз о составе (до ~150 символов);
- либо оставить длинный текст для сайта, а для бота заполнить отдельное поле
  `composition` — короткий состав. Поле `composition` в API уже есть и бот его
  предпочитает описанию, сейчас оно просто пустое у части позиций.

Второй вариант лучше: сайт ничего не теряет.

### 2.4 Проверьте полноту меню

В каталоге ровно 12 позиций и ни одного напитка. Если это тестовый набор — всё в
порядке, скажите, и мы не трогаем. Если это боевое меню, то бот физически не
может предложить то, чего в каталоге нет: на вопрос «а кола есть?» он честно
ответит «нет». Отсутствие позиции в каталоге для бота означает «этого нет в
ресторане».

## 3. Поле `price_amount_minor` содержит целые тенге, а не тиыны — просьба уточнить

Сейчас в ответе `catalog.context.get`:

```json
{ "currency": "KZT",
  "name": "Неаполитанская",
  "price_amount_minor": 3000,
  "compare_at_price_amount_minor": null }
```

По названию `_minor` значение должно быть в минорных единицах, то есть 3000
тиын = **30 ₸**. Но на витрине эта пицца стоит **3 000 ₸**, то есть в поле лежат
целые тенге. Мы сверились со страницей и читаем значение как тенге — у нас всё
считается верно, менять на нашей стороне нечего.

Проблема в другом: это ловушка для любой следующей интеграции. Кто угодно,
прочитав название поля, разделит на 100 и занизит цены в 100 раз. Просьба выбрать
одно:

- переименовать поле в `price_amount` (или `price`) — самый чистый вариант;
- либо оставить имя и действительно присылать тиыны (`300000`) — тогда
  **предупредите нас заранее**, мы поменяем чтение в тот же день. Если это
  случится без предупреждения, бот начнёт называть гостю цену 30 ₸ вместо 3000 ₸.

То же поле-в-поле касается `compare_at_price_amount_minor` и
`bonus_earn_amount_minor`.

Про `compare_at_price_amount_minor`, чтобы не было расхождения в трактовке: мы
считаем его **старой, зачёркнутой** ценой, а `price_amount_minor` — актуальной.
Например Донер: `price=1000`, `compare_at=1200` → гостю называется 1000 ₸ и
упоминается скидка. Если у вас смысл обратный — скажите, это меняет то, какую
цену бот обещает гостю.

## Что мы уже проверили — тут менять ничего не нужно

Чтобы не искали проблемы там, где их нет:

- `catalog.context.get` присылает `id` нормальными UUID — раньше был `0`, сейчас
  исправно;
- `available` приходит булевым, бот не предлагает распроданное;
- `category_id` / `category_name` заполнены у всех 12 позиций;
- подпись, окно в 5 минут и идемпотентность по `X-Command-Id` работают;
- `runtime.status.get` отдаёт `accepting_orders` и время ожидания корректно;
- `order.status_changed` доходит до гостя в WhatsApp — проверено на трёх реальных
  событиях.
